# 嘎嘎安全助手社区共建

J4team 维护的本地蓝队工作台。第一轮投稿通过发布本文的公众号后台接收，由团队整理分析。线上仓库、讨论区与群聊仍待确认后公布；本目录不代表这些外部服务已经创建。

仓库入口上线前，下表中的需求、规则、文章与模板均可先发公众号后台。说明投稿类型、使用场景、痛点、期望效果、脱敏示例和署名意愿；公众号后台不接收真实恶意样本、未公开漏洞或客户原始证据。

## 参与方式

| 想贡献什么 | 建议入口 | 有用的材料 |
|---|---|---|
| 可复现问题 | Bug Issue | 版本、系统、脱敏步骤、实际与预期结果 |
| 功能或体验 | 功能 Issue / 需求讨论 | 场景、当前操作、最小改进、验收方法 |
| 规则与日志适配 | 规则投稿 Issue | 行为说明、正反样例、定位预期、覆盖缺口 |
| 调查或样本研究文章 | 案例投稿 Issue | 已授权脱敏文章、证据结构、Hash 或公开报告链接 |
| 报告模板 | 模板投稿 Issue | 可编辑结构、适用场景、字段说明、许可归属 |
| 代码与文档 | 先讨论范围，再提交 PR | 变更说明、验证结果、边界和贡献者归属 |

还不会写代码，也可以帮助复现、补文档、改交互、做翻译，或验证实际平台兼容性。测试记录必须写明环境与材料来源，固定响应不能标成真实官方模型验证。

## 建议讨论区分类

- 公告：维护者发布版本、验证边界与社区事项。
- 需求池：用户描述任务，维护者评估范围，参与者认领。
- 规则与适配：讨论日志格式、检测逻辑、正常反例及回归材料。
- 案例与文章：脱敏调查过程、报告写法、研究方法。
- 使用互助：配置、操作与可复现问题；确认 Bug 后转 Issue。
- 体验反馈：窗口布局、键盘、无障碍与操作步骤。

这些是仓库启用 Discussions 后的建议分类；当前尚未在线创建。

## 从投稿到版本

投稿 → 待分诊 → 需补充 / 已评估 → 可认领 → 实现中 → 待复核 → 待验收 → 随版本发布。

建议用 `type:bug`、`type:feature`、`type:rule`、`type:case`、`type:template` 和 `status:*` 标签。标签需要维护者在实际仓库创建，表单不依赖尚不存在的标签。

维护者说明采纳、暂缓或不采纳的理由；范围较大的需求先做设计，避免重复开发。没有固定响应时限、合并保证或默认稿酬。涉及付款或奖励的征集须另行明确规则，本次不设自动奖励承诺。

## 投稿者权益与署名

请保留原作者和参考资料来源。署名、昵称或匿名方式以投稿者确认结果为准；不要公开不愿展示的联系方式。贡献者保留其贡献的版权，提交时确认有权按当前项目许可提供内容；不要求转让版权。素材涉及第三方许可时单独注明。

项目当前为非商用源码许可，具体以根目录 LICENSE.txt 为准。社区投稿不改变第三方权利，也不把当前许可转为 AGPL。提交代码前见 [贡献指南](../../CONTRIBUTING.md)，文章格式见 [投稿模板](SUBMISSION.md)。

## 材料与讨论规则

只讨论授权的防御、分析和研究场景。公开区不提交客户原始材料、个人信息、API Key、Agent 任务凭据、未公开漏洞或真实恶意二进制。样本研究提交 Hash、公开资料链接与脱敏结论；没有建立私密渠道前，不通过公共附件传递样本。漏洞披露遵守 SECURITY.md。

对结论提出证据，对参与者保持尊重；不攻击个人、不诱导泄露信息、不发布广告和未授权推广。维护者可对违规公开内容隐藏或关闭，并说明处理理由；敏感信息应先移除再讨论。

## 上线清单

1. J4team 确认实际仓库和维护者，确定许可最终版及公开联系渠道。
2. 将本目录、贡献指南及 `.github/ISSUE_TEMPLATE/` 文件放入仓库默认分支。
3. 启用 Issues 与 Discussions，建立上述分类及类型/状态标签。
4. 开启平台提供的私密安全报告功能，确认真实联系渠道后更新 SECURITY.md。
5. 发布欢迎帖、功能路线图和征稿启事，置顶实际入口。
6. 群聊用于交流，需求和处理结论回到仓库留档；群二维码只通过已确认的官方账号发布。
7. 完成后替换公众号稿中的筹备说明；不要提前宣称群、仓库或私密通道已上线。
